腾讯开源的 Go 语言 LLM 知识平台，以 RAG 问答、ReAct 智能体与自动维护的 Wiki 三种方式，把原始文档转化为可查询、可推理的知识资产。

## 项目做什么

项目目标是把散落的原始文档转化为可查询、可推理的知识资产：通过 RAG 支持日常快速问答，通过 ReAct 智能体自主编排知识检索、MCP 工具、技能沙箱与联网搜索来完成多步任务，并通过 Wiki 模式让智能体把原始文档沉淀成结构化、互相链接的 Markdown 知识库。同时提供多数据源接入、多模型与多存储后端替换、多工作区权限与审计等面向企业落地的能力，并支持本地或私有云自托管，以保留数据主权。

## 与同类方案相比

按 README 自述，优势集中在集成面与可替换性：可对接飞书、飞书云盘、GitLab、腾讯 IMA、Notion、语雀、钉钉文档、RSS 等数据源，支持 PDF、Word、图片、Excel、XMind 等 10 余种格式，兼容 OpenAI、DeepSeek、Qwen、智谱、混元、Gemini、MiniMax、NVIDIA、LiteLLM、Ollama 等 20 多个模型提供方，Office 文件可用 anydoc 在进程内解析。架构模块化，LLM、向量库与存储后端均可替换，支持多工作区 RBAC、审计日志、Langfuse 可观测与任务队列治理，也可通过 MCP、API Key、CLI 做程序化集成。以上均为 README 自述，未见第三方基准验证。

## 设计与创新

README 强调的差异化设计包括：Wiki 模式由智能体自动生成互相链接的 Markdown 页面并配知识图谱，附带手动编辑、逐行 diff 与一键回滚；检索分块可像文档一样编辑、版本比对与还原，并自动重建索引；租户技能目录配合会话级持久的 Docker、E2B、Cube 沙箱运行技能；跨会话长期记忆记录画像、偏好、事实、任务与兴趣。这些能力在同类开源 RAG 项目中较少同时出现，但 README 未提供与竞品的对比数据，因此无法验证其是否属于行业首创，也无法验证可量化的领先性。

## 适用场景

典型场景包括：企业或团队内部的制度、产品与技术文档问答检索；需要多步推理与工具调用的任务，例如先检索资料再调用沙箱脚本生成 Word 文档；把长期积累的非结构化资料整理成可持续维护的内部 Wiki 与知识图谱；通过企业微信、飞书、Slack、Telegram、钉钉等 IM 渠道以及网页嵌入组件对外提供问答入口；知识库规模较大的场景，README 称 Wiki 摄取可扩展到 4 万文档级知识库；以及要求数据不出内网的私有化部署，和通过 MCP、API Key、CLI 完成自动化集成与运维。

## 谁会受益

对希望自建知识问答系统的团队，它把文档解析、切分、向量化、检索、重排、模型推理、权限与可观测等环节打包成可替换模块，减少从零搭建的工作量；对已有大量文档但检索困难的机构，它提供文件夹树、批量标签、分块编辑与版本回滚等知识治理手段；对需要多步自动化的用户，智能体、技能沙箱与 MCP 工具链可把问答扩展到实际任务执行。由于支持自托管与多模型接入，也适合对数据主权或模型选型有要求的场景。实际收益仍取决于部署规模与数据质量，README 未给出效果数据。

## 使用前需要注意

README 未提供吞吐、延迟、召回准确率等性能指标，也未给出与其他 RAG 平台或知识管理方案的对比数据，因此性能表现和相对优势无法验证。系统组件较多，部署需自行准备并配置 LLM、向量库、对象存储、消息队列等依赖，运维与学习成本不低；版本迭代频繁，README 标注为 0.8.0 且更新日志密集，接口与功能可能持续变动，升级需关注兼容性。技能沙箱依赖 Docker、E2B 或 Cube 等运行时，且本地宿主机进程后端已被移除；部分数据源、模型与存储驱动的可用性依赖外部服务，需自行验证。README 徽章显示许可证为 MIT，具体条款应以仓库 LICENSE 文件为准。
