Paperclip 是开源 AI 代理团队编排平台，用 TypeScript 编写，提供目标定义、招聘代理、审批运行三步流程，将 Claude Code、Codex、OpenClaw 等代理组织成有架构图、预算与治理的公司。

## 项目定位与要解决的问题

Paperclip 定位为管理 AI 代理的应用程序，而非代理框架或聊天机器人。README 用“如果 OpenClaw 是员工，Paperclip 就是公司”的比喻说明其层级：它不告诉用户如何构建代理，而是管理这些代理工作的组织环境。项目面向拥有大量代理、需要协调多代理向共同目标推进的团队，尤其是同时打开多个 Claude Code 终端、希望代理 24/7 自主运行但仍可审计和干预的用户。README 明确列出适用与不适用场景：单代理用户可能不需要，二十个代理用户则“肯定需要”。

## 核心能力

核心是四个支柱：代理任务管理器、代理组织架构图、代理员工培训、代理操作系统。任务管理器让用户声明意图、代理工作、用户验证输出，支持审批与审查门禁；组织架构图定义角色、权限和人类与代理混合的汇报线；员工培训提供技能工作室、共享组织技能、评估和保存测试运行；操作系统提供跨提供方运行时、沙箱、集成、MCP 服务器、SSO、GRC、RBAC 和成本控制。所有任务都追溯到组织使命，代理知道做什么以及为什么。

## 技术结构与实现思路

架构上是一个 Node.js 服务器加 React UI，README 称其为完整控制平面。服务器包含身份与访问、工作与任务、心跳执行、治理与审批、组织架构与代理、工作区与运行时、插件、预算与成本、例程与调度、机密与存储、活动与事件、公司可移植性等系统。代理通过适配器接入，图中示例包括 Claude Code、Codex、Cursor、Gemini、bash、OpenClaw 等 CLI、HTTP/webhook 机器人及外部适配器插件。嵌入式 PostgreSQL 自动创建，开发时 API 服务启动在 3100 端口。

## 实际工作流程

工作流从定义目标开始，例如“打造第一的 AI 笔记应用达到 100 万美元 MRR”；然后招聘团队，包括 CEO、CTO、工程师、设计师、营销人员，任意机器人任意提供方；接着审批并运行，审查策略、设置预算、开始执行、从仪表盘监控。代理通过心跳按计划唤醒，检查工作并行动，委派沿组织架构上下流动。任务可分配给代理，代理在任务上下文中工作直至完成，用户审核工作产品。例程由 cron、webhook 或 API 触发，每次执行创建跟踪问题并唤醒指定代理。预算达到硬停止时暂停代理并取消排队工作。

## 与同类方案的取舍

README 强调 Paperclip 处理困难的编排细节：任务检出和预算执行是原子的，避免重复工作和失控花费；代理状态持久化，跨心跳恢复同一任务上下文；运行时技能注入让代理无需重新训练即可学习 Paperclip 工作流；治理带回滚，审批门禁强制执行、配置变更有版本可回滚；任务携带完整目标祖先信息；公司模板可导出导入并清理机密；真正的多组织隔离使每个实体都限定在公司范围内。与 OpenClaw、Claude Code 的区别在于 Paperclip 使用这些代理作为组件，将它们编排成有组织架构、预算、目标和问责制的公司，而非替代它们。

## 值得关注的设计

Paperclip 的核心主张是把代理管理从“一堆脚本”提升为“一家公司”：它把任务、组织、培训与基础设施四个层面统一到同一控制平面。任务被建模为带公司、项目、目标与父任务关联的工单，并采用原子化签出与执行锁，项目方自述可避免重复工作和失控开销；心跳执行由数据库支持的唤醒队列驱动，支持合并唤醒、预算检查、工作区解析、密钥注入与技能加载。它还强调持久代理状态，使代理在多次心跳之间续接同一任务上下文而非重来；运行时技能注入让代理在不重新训练的情况下学习工作流；治理带有版本化与回滚，审批门被强制执行。这些机制是 README 自述的设计目标，而非第三方验证的性能结论。

## 适用领域和具体场景

典型用法是先定义业务目标（例如做一款订阅收入达到百万美元的 AI 笔记应用），再按岗位“招聘”CEO、CTO、工程师、设计与市场等代理，随后审批策略、设定预算并监控。它覆盖的日常场景包括：任务分派与验收，代理按心跳周期自主唤醒并领取工作，定期例行任务如客服、社交媒体与报告由 cron、webhook 或 API 触发；成本按公司、代理、项目、目标、工单、供应商与模型维度统计并设预警阈值与硬停；多组织部署下同一实例运行多家公司并保持数据隔离；还能导出导入整个组织及其代理、技能、项目与例行任务，用于复制团队模板。

## 哪些人会受益

README 明确列出目标使用者：想搭建自主 AI 组织的人、需要把 OpenClaw、Codex、Claude 与 Cursor 等异构代理协调到同一目标的人、同时开着约二十个 Claude Code 终端而难以跟踪进度的人、希望代理 7×24 自主运行但仍能审计与随时介入的人、关注成本并要执行预算的人，以及希望像使用任务管理器一样管理代理流程的人。它同时面向管理者（用工组织图、权限与治理）、赋能者（技能工作室与评估）和 IT 平台团队（运行时、沙箱、单点登录、GRC、RBAC 与成本控制）。README 特别说明：如果你只有一个代理，可能不需要它；有二十个则几乎一定需要。

## 上手、部署与集成

采用路径以自托管为主，官方强调开源、无需 Paperclip 账号。安装脚本会检查 Node.js 24.11 或更新版本，把受管 CLI 装到用户目录并启动交互式引导，还可在部分 Linux 与 macOS 系统注册为后台服务；脚本随附校验和，但 README 也提醒校验文件与脚本同源，需要独立来源时应使用带发布标签或提交哈希的 GitHub 副本。也可以直接通过 npx 试用而不做永久安装，或用 test-drive 启动已预置 CEO 代理的隔离实例。手动方式为克隆仓库、用 pnpm 安装并运行开发命令，服务在本地启动并自动创建嵌入式 PostgreSQL，无需额外配置，生产环境可指向自有 Postgres。

## 限制与风险

README 用专门章节划定边界：它不是聊天机器人，代理有岗位而非聊天窗口；不是代理框架，不教如何构建代理；不是工作流搭建器，没有拖拽式流水线；不是提示词管理器，代理自带提示词、模型与运行时；不是单代理工具，更偏向多代理团队；也不是代码审查工具，只编排工作本身。官方还承认自带工单系统对接仍在路线图上，快捷安装脚本的校验和与脚本同源，管道执行方式要求本机已具备受支持的 Node.js、npm 与 npx，若需引导 Node.js 则建议先下载审阅脚本。文档给出的是架构与流程能力，具体性能与可靠性表现未有第三方基准支撑。

## 综合观察

Paperclip 的定位差异不在模型能力，而在组织与治理层：它把票务、组织架构、预算硬停、审批与审计日志做进同一控制平面，并宣称任务签出与预算执行是原子的、代理状态跨心跳持久、治理变更可回滚，这些均为项目方自述，README 未给出可独立复核的对比测试。对同时运行多个异构代理、又被成本与协调问题困扰的团队，它提供了比手工维护配置文件夹更系统的结构；对只有单个代理的用户，官方自己也建议不必引入。其价值上限取决于实际部署中的可靠性与运维成本，采用前宜按文档自述逐项验证，尤其是多组织隔离、预算停机和密钥作用域等安全相关承诺。
